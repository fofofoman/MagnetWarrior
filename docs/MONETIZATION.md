# 수익화

## 원칙: Pay-to-win은 코드로 막는다

자석 파워 강화 아이템을 팔지 않겠다는 것은 문서상의 다짐이 아니라 부팅 시 검사다.
모든 판매 항목은 `impact` 필드를 선언해야 하고, 허용되는 값은 두 개뿐이다.

| `impact` | 의미 |
| --- | --- |
| `"None"` | 순수 외형. 게임플레이에 어떤 영향도 없음 |
| `"Convenience"` | 주행 **바깥**의 시간을 절약. 주행 안에서는 아무 효과 없음 |

`MonetizationConfig.Validate()`는 서버 시작 시 가장 먼저 실행되며, 다른 값을 선언한 상품이
하나라도 있으면 경고가 아니라 **에러로 서버를 세운다**.

```lua
assert(
    legalImpacts[product.impact],
    `[PAY-TO-WIN GUARD] ... 자석 파워·주행 시간·점수에 영향을 주는 것은 금지`
)
```

실수로 밸런스에 영향을 주는 상품을 출시하는 것은 로그 한 줄로 넘어갈 일이 아니라 배포를 막아야
할 일이기 때문이다. 카테고리가 `Cosmetic`인데 `impact`가 `"None"`이 아닌 경우도 별도로 막는다.

두 번째 방어선은 `MonetizationService`의 `grants` 테이블이다. **돈으로 할 수 있는 일의 전체
목록**이 거기 한 곳에 있고, 자석 힘·타이머·기록에 닿는 코드는 그 테이블 어디에도 없다.

## 판매 항목

### 1순위 — 코스메틱 게임패스

| 키 | 이름 | 내용 |
| --- | --- | --- |
| `MagnetColorPack` | 자기장 컬러 팩 | Pull/Push 이펙트 색상 8종 |
| `TrailPack` | 이동 트레일 팩 | 고속 이동 시 트레일 4종 |
| `VictoryPosePack` | 승리 포즈 팩 | 클리어 시 재생되는 승리 연출 4종 (경례·부양·압쇄·극성) |

승리 연출은 `client/Effects/VictoryPose.luau`가 프리미티브로 직접 만든다. 애니메이션 에셋
업로드는 이 저장소가 할 수 없는 단계이고, 에셋을 기다리는 코스메틱은 존재하지 않는 코스메틱이기
때문이다. 각 연출에 `animationId` 슬롯이 비어 있으니 나중에 실제 애니메이션을 얹을 수 있다 —
사운드의 `assetId`와 같은 방식이고, 연출 자체는 그것 없이도 재생된다.

연출은 **서버가 전체에게 브로드캐스트**한다. 어떤 연출인지는 보내지 않는다 — 선택값이 이미
`Pose` 어트리뷰트로 복제되고 있으므로, 각 클라이언트가 알아서 해석한다. 사는 사람만 볼 수 있는
코스메틱은 반쪽짜리 상품이다.

> **검증됨.** `scratchpad/invariants.py`가 "판매되는 모든 코스메틱 값에 그리는 코드가
> 있는가"를 검사한다. 승리 포즈 팩은 실제로 이 검사 없이 *팔리지만 아무것도 그리지 않는* 상태로
> 존재했다 — 패스도 있고, 선택지도 뜨고, 서버 검증도 통과하는데 `Pose` 어트리뷰트를 읽는 코드가
> 어디에도 없었다.

착용 요청은 서버가 검증한다. 보유하지 않은 값을 요청하면 거부되고, 확정된 값은 `Player`
어트리뷰트로 게시된다. 어트리뷰트는 모든 클라이언트에 자동 복제되므로 다른 플레이어의 빔 색상을
보여주기 위한 별도 원격이 필요 없다.

환불에 대비해 **적용 시점에도 다시 검증**한다. 패스가 사라졌다면 기본값으로 되돌린다.

### 2순위 — 편의 게임패스

| 키 | 이름 | 내용 |
| --- | --- | --- |
| `CheckpointSave` | 체크포인트 저장 | 세션이 끊겨도 마지막 체크포인트에서 재개 |
| `VipServer` | VIP 프라이빗 서버 | 친구들과 단독 서버에서 연습 |

`CheckpointSave`가 저장하는 것은 **연습 위치뿐이다.** 기록용 주행은 여전히 출발 볼륨부터
시작해야 하므로 측정 시간을 줄일 수 없다. 이것이 이 상품이 `Convenience`로 분류될 수 있는
이유다.

### 3순위 — 개발자 상품 (소모품)

| 키 | 이름 | 내용 |
| --- | --- | --- |
| `SkipRetryWait` | 즉시 재시도 | 리스폰 대기시간(3초)을 건너뜀 |
| `GhostReplayTicket` | 고스트 리플레이 열람권 | 상위 랭커 주행 1회 열람 |

`SkipRetryWait`이 건드리는 대기시간은 `RespawnService`가 관리하는 사망 후 대기이고, 타이머는
출발 볼륨 진입 시점에 시작하므로 기록과 무관하다.

`GhostReplayTicket`이 사는 것은 **열람**이다. 고스트는 반투명 실루엣으로 나와 같이 달릴 뿐
충돌하지도, 주행에 영향을 주지도 않고, 그 기록이 몇 초인지는 이미 랭킹판에 공개되어 있다.
영상으로 볼 수도 있었을 루트를 편하게 보는 값이므로 `impact = "None"`이다.

두 가지 안전장치가 있다.

- **자기 기록은 절대 소모하지 않는다.** 개인 고스트는 무료이고, 1위가 본인이면 그것도 무료다.
- **한 세션에 스테이지당 한 번만 과금한다.** 패널을 다시 열거나 죽어서 재접근할 때 두 번
  걷히지 않도록, 이미 연 스테이지는 세션 동안 기억한다 (`GhostService.unlockedBest`).

## 자산 ID 연결

모든 `assetId`가 `0`으로 되어 있다. 크리에이터 대시보드에서 상품을 만든 뒤 그 숫자를
`src/shared/Config/MonetizationConfig.luau`에 넣으면 된다.

```lua
{
    key = "MagnetColorPack",
    assetId = 123456789,   -- ← 여기
    ...
}
```

`assetId = 0`인 항목은 크래시가 아니라 "아직 판매 준비 중입니다" 안내로 처리된다. 게시 전에도
Studio에서 게임이 정상 동작한다.

Studio 테스트 편의를 위해 `GameConfig.Debug.GrantCosmeticsInStudio = true`이면 코스메틱 패스를
보유한 것으로 취급한다. 코스메틱 한정이며, 애초에 게임플레이에 영향을 주는 것이 없으므로 이
편의 기능이 밸런스로 새어나갈 여지가 없다.

## 영수증 처리 (중복 지급 방지)

로블록스는 `ProcessReceipt`가 `PurchaseGranted`를 반환할 때까지 같은 영수증을 계속 재전달한다.
따라서 멱등성이 없으면 한 번의 결제가 여러 번 지급된다.

처리 순서는 다음과 같다.

```
1. 프로필의 purchaseHistory에 이미 있음  → PurchaseGranted (이미 영구 기록됨)
2. 이번 세션에 아직 적용 안 했으면       → 지급 1회 적용
3. purchaseHistory에 기록 + 즉시 저장
4. 저장 실패                              → 기록 되돌리고 NotProcessedYet
                                            (재전달 시 2번은 건너뛰고 저장만 재시도)
5. 저장 성공                              → PurchaseGranted
```

핵심은 **저장에 성공한 뒤에만 승인한다**는 것이다. 저장이 실패하면 영수증을 승인하지 않으므로
로블록스가 다시 보내고, 아무것도 영구 저장되지 않았으니 다음 세션에서의 재전달이 올바른
동작이 된다. 반대로 세션 내 재시도에서는 `grantedThisSession`이 중복 적용을 막는다.

플레이어가 이미 나갔다면 `NotProcessedYet`을 반환한다. 영수증이 살아남아 다음 접속 때 다시
전달된다.

## 확장 지점 (지금 구현하지 않음)

`MonetizationConfig.PlannedRevenueStreams`에 자리를 잡아 두었다.

```lua
MonetizationConfig.PlannedRevenueStreams = {
    SeasonPass    = { enabled = false, allowedImpact = "None" },
    RewardedVideo = { enabled = false, allowedImpact = "None" },
}
```

둘 다 붙을 자리가 이미 정해져 있다.

- **시즌 패스**는 결국 또 하나의 게임패스이고, 그 보유 여부가 코스메틱 트랙을 여는 형태가 된다.
  진행도 필드는 `DataService`의 마이그레이션으로 추가하면 되며 기존 기록은 건드리지 않는다.
- **리워드 비디오**는 구매가 아닌 지급이므로 `Entitlements.Grant()`를 그대로 탄다. 이 함수는
  `MonetizationConfig`에 선언되지 않은 키를 거부하므로, 새 기능이 Pay-to-win 검사를 우회해서
  엔타이틀먼트를 만들어낼 수 없다.

두 경우 모두 `allowedImpact`가 `"None"`으로 못 박혀 있고, `Validate()`가 이 값도 함께 검사한다.

## 왜 이렇게까지 하나

기록판이 있는 게임에서 "돈 주고 산 사람이 위에 있다"는 인식이 한 번 생기면 랭킹은 그 순간
의미를 잃고, 랭킹이 의미를 잃으면 반복 플레이의 이유도 함께 사라진다. 자석전사의 수익 모델은
랭킹의 신뢰도 위에 서 있으므로, 그 신뢰도를 깨뜨릴 수 있는 코드 경로를 아예 없애는 편이 장기
매출에 유리하다.
