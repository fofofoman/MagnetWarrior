# 기록 검증 (Anti-Cheat)

랭킹이 있는 게임에서 기록 검증은 부가 기능이 아니라 게임의 신뢰도 그 자체다. 이 문서는
"클라이언트 타이머 신뢰 금지"와 "비정상 이동/스킵 필터링"이 코드상 어디에서 어떻게 강제되는지를
정리한다.

## 대전제

**클라이언트는 시간을 보고하지 않는다.** 보고할 방법 자체가 없다. `Net.luau`의 원격 목록에
클라이언트가 시간을 보낼 수 있는 통로가 아예 존재하지 않는다. 서버는 다음 세 순간을 직접
관측한다.

1. 플레이어가 출발 볼륨 안에 있는 것을 서버가 관측 → 타이머 시작
2. 체크포인트 볼륨 통과를 서버가 관측 → 구간 기록
3. 도착 볼륨 안에 있는 것을 서버가 관측 → 타이머 정지

관측은 `RunSessionService`가 20 Hz로 도는 오버랩 질의로 수행한다. `Touched` 이벤트에 의존하지
않는 이유는 아래 "터널링" 항목에 있다.

HUD에 흐르는 숫자는 `RunState.Elapsed()`가 서버 시각으로부터 보간한 **표시용 추정치**이고,
기록에 반영되는 값은 서버의 `os.clock()` 차이다. 둘은 애초에 다른 값이며 클라이언트 쪽 숫자는
어디에도 전달되지 않는다.

## 검증 계층

주행 하나가 기록으로 남으려면 아래 다섯 관문을 전부 통과해야 한다. 하나라도 실패하면
`RunSessionService.Finished`는 `valid = false`로 발화하고, `RecordService`는 그 결과를 저장하지
않는다. 플레이어에게는 사유와 함께 "기록 무효" 카드가 뜬다 — 조용히 버리지 않는다.

### 1. 체크포인트 순서 (스킵 필터)

`reachCheckpoint`는 `info.index ~= run.nextCheckpoint`이면 아무 일도 하지 않는다. 즉 3번
체크포인트를 먼저 밟아도 인정되지 않고, 나중에 도착 볼륨에 들어와도

```lua
if run.nextCheckpoint <= definition.checkpointCount then
    return false, "checkpoint skipped"
end
```

에서 거부된다. 스테이지 중간을 뛰어넘는 경로는 완주 자체가 성립하지 않는다.

지오메트리도 같은 규칙을 뒷받침한다. 게이트는 퍼즐 완성/적 전멸 전까지 물리적으로 닫혀 있으므로
(예: 6번 스테이지의 다리 게이트) 운 좋은 발사로 협곡을 건너뛰어도 그 다음이 막혀 있다.

### 2. 절대 최소 시간

스테이지마다 `StageConfig.minPossibleMs`가 있다. 임계 경로 길이를
`MagnetConfig.MaxLegitimateSpeed`로 나눠 산출한, **인간이 물리적으로 낼 수 없는 하한**이다.

```lua
if timeMs < definition.minPossibleMs then
    return false, "impossible time"
end
```

골드 기준시간보다 한참 아래로 잡혀 있다. 이 값은 루트 최적화를 벌하기 위한 게 아니라 텔레포트를
잡기 위한 것이다.

### 3. 구간별 최소 시간

총합만 검사하면 "스테이지 절반을 클립으로 통과하고 나머지를 정상 주행"하는 경우를 놓친다. 그래서
각 구간(출발→CP1, CP1→CP2, …)에도 하한이 있다.

```lua
local segmentFloor = (definition.minPossibleMs / segmentCount) * SEGMENT_FLOOR_FACTOR
```

`SEGMENT_FLOOR_FACTOR = 0.4`로 넉넉하게 잡았다. 구간별 편차가 큰 루트 최적화는 실력이고, 구간
하나를 0.1초에 통과하는 건 실력이 아니다.

### 4. 이동 감사 (`MovementAudit`)

캐릭터의 물리는 소유 클라이언트가 시뮬레이션한다. 이건 로블록스의 구조이고 바꿀 수 없다. 대신
서버는 **캐릭터가 실제로 어디에 도달했는지**를 10 Hz로 표본화하고, 그 경로가 물리적으로 가능한지
판정한다.

축을 나눠서 본다. 한계가 실제로 다르기 때문이다.

| 축 | 기본 한계 | 부스트 중 한계 |
| --- | --- | --- |
| 수평 | 34 studs/s | `MaxLegitimateSpeed` (140) |
| 상승 | 62 studs/s (점프력 여유 포함) | `MaxLegitimateSpeed` |
| 하강 | 320 studs/s (낙하는 빠르고 합법) | 동일 |

핵심은 **"부스트 중"의 정의**다. `MagnetService`는 정당한 힘을 적용할 때마다
`MovementAudit.NoteBoost()`를 호출하고, 그 후 1.2초 동안만 한계가 올라간다. 서버가 힘을 준 적
없는데 발생한 속도는 설명이 없는 속도이고, 그대로 위반으로 집계된다.

- **하드 플래그**: 한 표본에 55 studs 이상 이동 (10 Hz 기준 약 550 studs/s). 어떤 힘으로도
  불가능 → 즉시 무효.
- **소프트 플래그**: 축별 한계 초과. 랙이나 물리 스텝 요동으로 가끔 발생할 수 있으므로 6회까지
  허용하고, 그 이상이면 무효.

서버가 의도적으로 위치를 옮기는 경우(리스폰, 체크포인트 복귀, 스테이지 이동)는
`MovementAudit.Forgive()`로 직전 표본을 버린다. 이게 없으면 정상적인 텔레포트가 전부 핵으로
잡힌다.

### 5. 사망 = 무효

사망하면 `abortRun(player, "died")`로 주행이 즉시 종료된다. 랭킹의 의미를 "한 번에 클리어한
시간"으로 고정하기 위해서다. 덕분에 체크포인트를 연습용 리스폰 지점으로 겸용해도 기록이 흐려지지
않는다.

## 코어 메카닉 쪽 방어

기록 검증 이전에, 자석 자체가 조작될 수 없어야 한다.

### 원점 위조 차단

클라이언트는 조준 광선의 시작점을 보내지만, 서버는 그것이 **실제 머리 위치 근처인지** 확인한다.

```lua
if (origin - anchorPosition).Magnitude > MagnetConfig.MaxOriginDeviation then
    feedback(player, action, "Rejected")
    return
end
```

맵 반대편에서 자석을 쏘는 조작이 여기서 끊긴다. 그래서 클라이언트는 3인칭 카메라 위치가 아니라
머리 위치를 원점으로 보내고, 방향만 카메라 조준점을 향하도록 다시 계산한다.

### 타겟 선택과 에임 어시스트는 서버가 한다

클라이언트는 "무엇을 맞췄는지" 보고하지 않는다. 서버가 직접 레이캐스트하고, 빗나갔을 때의 원뿔
보정(`coneAssist`)도 서버에서 수행하며 가시선까지 확인한다. 조작된 클라이언트가 "완벽하게
맞췄다"고 주장해서 얻는 이득이 없다.

### 물리 소유권 회수

`MagneticRegistry`는 자석 대상 파트에 `SetNetworkOwner(nil)`을 걸어 **서버가 시뮬레이션하도록**
강제한다. 이게 없으면 밀려난 상자가 어디로 얼마나 빠르게 날아가는지를 근처 클라이언트가
결정하게 되고, 충돌 데미지가 통째로 조작 가능해진다. 나머지 방어 장치 전부가 이 한 줄 위에 서
있다.

### 쿨다운과 레이트 리밋의 분리

쿨다운(`MagnetConfig.PullCooldown`)은 게임 디자인 수치이고, 레이트 리밋
(`RateLimiter`, 12/s + 버스트 6)은 보안 수치다. 둘을 분리한 이유는 명확하다 — 클라이언트가
쿨다운을 제거해도 토큰 버킷은 서버에 있다.

### 스테이지별 손 제한

1번 스테이지가 Pull 전용인 건 지오메트리 배치 때문이 아니라 서버가 거부하기 때문이다.

```lua
if stageId and not StageConfig.IsActionAllowed(stageId, action) then
    feedback(player, action, "Rejected")
end
```

### 원격 입력 소독

`MagnetAction` 핸들러는 페이로드를 적대적인 입력으로 취급한다. 타입 확인, NaN/무한대 확인
(`value.X ~= value.X`로 NaN 탐지), 좌표 크기 상한, 방향 벡터 길이 확인(0.9~1.1)을 모두 거친다.
클라이언트가 보낼 수 있는 모든 원격은 동일한 방식으로 검증되며, 조회성 원격은 별도의 레이트
리미터를 갖는다.

## 터널링 방지

빠르게 움직이는 플레이어가 판정 볼륨을 프레임 사이에 통과해 버리는 문제는 검증만큼 중요하다.
놓친 체크포인트는 정상 주행을 무효로 만들기 때문이다.

- **체크포인트**: 질의 반경을 속도에 비례해 넓힌다.
  `radius = BASE_TRIGGER_RADIUS + 속도 × 스캔 간격`. 140 studs/s로 날아가도 20 Hz 스캔 사이에
  이동한 거리만큼 반경이 커지므로 볼륨을 놓치지 않는다.
- **낙사 판정**: `Touched`를 쓰지 않는다. 4 studs 두께의 판을 낙하 중에 통과해 버릴 수 있기
  때문에, `HazardService`는 플레이어 좌표가 볼륨 아래인지를 직접 검사한다. 통과할 수 없는
  판정이다.
- **충돌 데미지**: `Touched`는 물리 스텝이 이미 속도를 반사시킨 뒤에 발화하므로, 그 시점의
  속도를 읽으면 타격이 과소평가되거나 0이 된다. `CombatService`는 비행 중인 물체의 속도를 매
  프레임 표본화해 두고 충돌 시 그 값을 쓴다.

## 판정 볼륨과 자석의 충돌 그룹 분리

체크포인트 볼륨은 서버의 오버랩 질의에는 잡혀야 하지만 자석의 레이캐스트에는 걸리면 안 된다.
체크포인트를 통과해 조준하면 자석이 허공을 맞는 버그가 되기 때문이다.

해결은 콜리전 그룹이다. 판정 볼륨은 `Trigger` 그룹에 들어가고, 이 그룹은 `Default`/`Player`와
비충돌로 설정된다. 오버랩 질의만 `CollisionGroup = "Trigger"`로 수행하므로 볼륨을 보고, 자석
레이캐스트는 기본 그룹이라 그대로 통과한다.

## 운영 시 확인할 것

거부된 주행은 서버 로그에 사유와 함께 남는다.

```
[RunSession] rejected PlayerName on stage_03_scrapyard: horizontal speed
  (peak 210 studs/s, 9 soft, 0 hard)
```

정상 플레이어에게서 소프트 플래그가 반복적으로 관측된다면 그건 핵이 아니라 `MovementAudit`의
한계값이 게임의 실제 속도와 어긋났다는 신호다. 특히 `MagnetConfig`의 추진력 수치를 올린 뒤에는
`MaxLegitimateSpeed`를 같이 올려야 한다. 두 값은 함께 움직여야 한다.
